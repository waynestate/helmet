# Use HELMET in raw PHP [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#use-helmet-in-raw-php)

This page boots HELMET in a framework-free PHP app with a single call. Start with [Boot the app](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#boot-the-app), then pick up the options your app needs: structured logs, the request-forgery guard, the opt-in error handler, the standalone health check and the readiness check.

## Boot the app [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#boot-the-app)

At the top of the front controller, before anything is echoed:

```php
use function Waynestate\Helmet\helmet_boot;

$helmet = helmet_boot([
    // The platform preset that supplies the trusted proxies. An explicit
    // 'trusted_proxies' list wins over the preset.
    'preset' => 'citadel',

    // Optional. A Monolog JSON logger, one line per record. "stream" may be a
    // stream or a file path. The presets supply trusted proxies only, so the
    // app picks its own log stream: on a platform like Citadel a file such as
    // /var/log/app/helmet.log, off the platform php://stderr. Every record
    // carries a request ID in extra.request_id, generated by HELMET; an
    // inbound header is never trusted for it. Set "request_id" to reuse an ID
    // you already have (8 to 64 letters, digits, dots, underscores or dashes).
    'log' => [
        'channel' => 'app',
        'stream'  => 'php://stderr',
        'level'   => 'info',
        // 'request_id' => 'req-20261029-abcd',
    ],
]);

// $helmet['nonce'] is the per-request CSP nonce. Put it in your <script> tags.
// $helmet['logger'] is a Psr\Log\LoggerInterface, or null when no log is set.
// $helmet['request_id'] is the ID stamped on this process's log records.
```

`helmet_boot()` sends the headers, strips `X-Powered-By`, and answers `/up` with `200 ok` before your code runs. It returns the nonce, the logger and the request ID so the rest of the app can use them.

It reads `$_SERVER` directly rather than building a PSR-7 request, so it works in plain PHP without a server-request factory. In order, it:

- sets up a JSON logger (when `log` is set),
- decides whether the request is HTTPS from the trusted-proxy list, and logs `helmet.forwarded_proto_rejected` when an untrusted peer sent `X-Forwarded-Proto`,
- hardens the session settings (throws if a session is already active),
- removes the `X-Powered-By` header,
- warns once through the logger when the trusted-proxy list holds a broad entry,
- registers the generic error page handler (when `error_handler` is enabled),
- answers the health check path with `ok` and stops,
- validates the readiness config (when `readiness` is set), so a typo fails at boot rather than on the first probe,
- rejects a state-changing request when the request-forgery guard is enabled and the request is not same-origin (or from a trusted origin),
- sends the security headers (including a per-request CSP nonce),
- answers the readiness path with the report (when `readiness` is enabled), after the headers,
- adds `Cache-Control: no-store` to matching responses (when `no_store` is enabled and they do not set it themselves).

Note

A bad config throws at boot: `UnknownPresetException` if `"preset"` names a preset the package does not know, `\InvalidArgumentException` for a wrong type or an invalid value, `InvalidCspReportUriException` if `"csp_report_uri"` is not a valid report destination, and `\LogicException` if a session is already active.

## Structured logs [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#structured-logs)

Each record is one JSON line:

```json
{"message":"login","context":{"user":"alice"},"level":200,"level_name":"INFO","channel":"app","datetime":"2026-10-29T12:00:00.000000+00:00","extra":{"request_id":"9f2c1ab04d5e6f70"}}
```

When you set `log`, the channel defaults to `helmet`, the stream to `php://stderr`, and the level to `info`. The request ID rules sit in the boot snippet above: every record carries one in `extra.request_id`, generated by HELMET, and an inbound header is never trusted for it.

## Security events [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#security-events)

Five warnings carry HELMET's security events, and a logger that throws never changes the answer: the `403` still goes out, the resolved client IP is still the peer, the HTTPS decision stands, and the boot still finishes.

| Message | When | Context keys |
| --- | --- | --- |
| `helmet.request_refused` | the request-forgery guard answers `403` | `event` (`request_refused`), `method` (upper case), `path` (no query string), `sec_fetch_site` (`same-origin`, `same-site`, `cross-site`, `none`, `other`, or null when the header is absent), `origin_present` (bool) |
| `helmet.forwarded_for_rejected` | `ClientIp::resolve()` fails closed on an unparseable `X-Forwarded-For` entry: in `helmet_metrics()` and in the Laravel metrics endpoint | `event` (`forwarded_for_rejected`), `reason` (`unparseable_entry`), `peer` (the trusted peer address) |
| `helmet.forwarded_proto_rejected` | the HTTPS check sees `X-Forwarded-Proto` from a peer that is not a trusted proxy, and ignores it: in `helmet_boot()`, `SecurityHeadersMiddleware` and the Laravel `SecurityHeaders` middleware | `event` (`forwarded_proto_rejected`), `reason` (`untrusted_peer`), `peer` (the untrusted peer address) |
| `helmet.broad_trusted_proxy` | the app boots with a broad entry in its trusted-proxy list (an IPv4 range shorter than `/16` or an IPv6 range shorter than `/48`) | `event` (`broad_trusted_proxy`), `entries` (the broad entries, as configured) |
| `helmet.debug_enabled_in_production` | the Laravel adapter boots with `app.debug` true in the production environment | `event` (`debug_enabled_in_production`) |

Never logged: the Origin value, cookies, Authorization, the `X-Forwarded-For` or `X-Forwarded-Proto` header, or the bad entry. The helmet takes the hit and reports it, without quoting the attacker.

The logger reaches each path this way: `helmet_boot()` hands its own logger to the HTTPS check, the broad-proxy warning and the guard; PSR-15 users pass a `LoggerInterface` as the last constructor argument `$logger` of `SecurityHeadersMiddleware` and of `RequestForgeryGuard` (both default to `null`, which logs nothing); `helmet_metrics()` passes its configured logger to `ClientIp::resolve()`; the Laravel adapter writes every event through the app's own logger.

## Trusted proxies [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#trusted-proxies)

Use a platform preset (for example `citadel`, which trusts the Docker bridge gateway), or list only the address the front proxy connects from, never a whole private range. A broad range such as `10.0.0.0/8` also trusts other containers on the same network, and any of them could then set `X-Forwarded-Proto`. An explicitly empty `HELMET_PROXIES` means trust nobody, even when a preset is set; only an unset variable falls back to the preset.

Warning

The `citadel` preset trusts the container bridge gateway address, which is only correct while the app's port is not published to the host network, because a published port can make a direct client appear to come from the gateway.

The trusted proxies come from, in order of precedence:

- `trusted_proxies`: an explicit list of IPs or CIDR ranges.
- `preset`: a platform preset name (see `Waynestate\Helmet\Platform\Presets`), for example `citadel` or `docker`.
- neither: an empty list, which trusts nothing.

## A generic error page [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#a-generic-error-page)

A raw PHP app has no framework to catch an uncaught exception, so PHP may print the message, the file path and a stack trace to the visitor. Turn on the opt-in handler and the visitor gets a short, fixed "Something went wrong" page with status 500 and `Cache-Control: no-store`, while the full detail (class, message, file, line and trace) goes to the log at `error` level:

```php
helmet_boot([
    'error_handler' => ['enabled' => true],
]);
```

The page never contains anything from the exception, and a logger that throws cannot change it. It is off by default, and Laravel keeps its own exception handler. If you want to build the page yourself, call `(new \Waynestate\Helmet\Error\GenericErrorResponse())->build($exception, $logger)` for the status, headers and body as data. HELMET does not switch PHP's `display_errors` off for you; the platform setting does that.

The same class builds the 4xx half of the rule. A raw PHP router answers a client fault with `helmet_client_error()`, the 4xx sibling of `helmet_forbidden()`: it sends the status, `Content-Type: text/html; charset=utf-8`, `Cache-Control: no-store` and the fixed page, then exits.

```php
use function Waynestate\Helmet\helmet_client_error;

if ($route === null) {
    helmet_client_error(404);
}
if (!in_array($_SERVER['REQUEST_METHOD'], $route['methods'], true)) {
    header('Allow: ' . implode(', ', $route['methods']));
    helmet_client_error(405);
}
```

`helmet_client_error_response($status)` returns the same answer as data (`status`, `headers`, `body`) without sending anything, the way `helmet_forbidden_response()` pairs with `helmet_forbidden()`, and `(new \Waynestate\Helmet\Error\GenericErrorResponse())->clientError($status)` is the class underneath both.

The page is fixed text: 400, 401, 403, 404, 405, 410 and 429 each carry their own title and sentence, and any other 4xx keeps the status you passed and falls back to the Bad request text. The functions take only the status code, so no message, path or exception can reach the body. Only 400 to 499 is accepted: a 500 or a redirect status throws `\InvalidArgumentException` before anything is sent, because a server fault belongs to the error handler and the log, not to a client-error page. Laravel apps get the same page for every 4xx HTTP exception with `HELMET_ERROR_PAGES=true` (see [Generic 4xx pages](https://helmet.apps.wayne.edu/docs/guides/usage-laravel.html#generic-4xx-pages)).

## Debug output stays off in production [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#debug-output-stays-off-in-production)

HELMET never switches debug output off or on for you, because the right place is the platform, not a library. Two settings decide whether a visitor can read a stack trace, and both belong to your deploy:

- **PHP's `display_errors`.** Keep it `Off` in production. Squire's deploy kit already ships a `php.ini` with `display_errors = Off` and `log_errors = On` (`deploy/.squire/php.ini` in a Squire-based app), and Citadel uses the same values. Off the platform, set it in `php.ini` or the FPM pool. HELMET does not set or check it.
- **Laravel's `APP_DEBUG`.** Keep it `false` in production. The Laravel adapter cannot stop an app from turning it on, but it notices: when the app boots with `app.debug` true in the production environment it writes one warning, `helmet.debug_enabled_in_production`, through the Log facade. Opt out with `helmet.warn_debug` (env `HELMET_WARN_DEBUG`, default `true`). A logger that fails never breaks the boot.

The opt-in error handler above covers one more case: with it on, an uncaught exception in a raw PHP app shows the fixed 500 page even if `display_errors` is wrong. Warnings and notices still follow `display_errors`, so set it anyway.

## Health check without a front controller [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#health-check-without-a-front-controller)

A raw PHP app with no front controller (or an Apache setup with no rewrite) never reaches `helmet_boot()` for `/up`. Ship a two-line `public/up.php` that calls HELMET directly:

```php
<?php // public/up.php
use function Waynestate\Helmet\helmet_up;

require __DIR__ . '/../vendor/autoload.php';
helmet_up();
```

Squire's raw template ships this file. The probe only checks that the ball is in the air; it does not grade the play.

`helmet_up()` sends exactly what `helmet_boot()` sends for the health path (`200`, `Content-Type: text/plain; charset=utf-8`, `Cache-Control: no-store`, body `ok`) and exits. No session, no other headers, no config read.

## Readiness is a separate check [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#readiness-is-a-separate-check)

`/up` is liveness: "the process is running". Keep it free of dependency checks. If `/up` fails because the database is down, the platform restarts a healthy app and makes the outage worse. Readiness, "send me traffic?", gets its own path. Turn it on with the `readiness` option:

```php
$helmet = helmet_boot([
    'preset' => 'citadel',
    'readiness' => [
        'enabled' => true,
        'checks' => ['database' => static fn (): bool => db_ping()],
    ],
]);
```

`GET /ready` then answers JSON, `200` or `503`, with HELMET's own config checks (headers, trusted proxies, debug output) next to yours, and no secrets. A raw app with no front controller answers from `public/ready.php` with `helmet_ready()`. The body, each check, and where each platform's probe should point are in [Readiness](https://helmet.apps.wayne.edu/docs/guides/readiness.html).

## The nonce in your markup [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#the-nonce-in-your-markup)

Tip

Vite's dev runtime reads a `<meta property="csp-nonce" nonce="...">` tag to nonce the CSS and preload tags it adds after page load. Print `helmet_csp_nonce_meta($helmet['nonce'])` in the `<head>` of every page, with the same nonce `helmet_boot()` returned. The nonce is escaped, so a nonce with a quote cannot break out of the attribute.

## Raw PHP with a Vue (Vite) build [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#raw-php-with-a-vue-vite-build)

A raw PHP app that serves a built Vue/Vite SPA gives the bundler HELMET's nonce in two steps. At build time, set Vite's `html.cspNonce` to a placeholder:

```js
// vite.config.js
import { defineConfig } from 'vite';

export default defineConfig({
    html: {
        cspNonce: 'CSP_NONCE_SLOT_FOR_HELMET',
    },
});
```

On every request, replace the placeholder with the nonce `helmet_boot()` returned before you echo the page:

```php
echo helmet_csp_nonce_swap(file_get_contents('dist/index.html'), $helmet['nonce']);
```

`helmet_csp_nonce_swap()` replaces every occurrence of the placeholder with the nonce, HTML-escaped exactly the way `helmet_csp_nonce_meta()` escapes it. A placeholder shorter than 16 characters throws, so it cannot collide with page text, an empty nonce throws, and a page that carries no placeholder is returned unchanged.

One more setting keeps the CSP honest: Vite inlines small assets as `data:` URIs by default. The default policy already allows `data:` in `font-src` and `img-src`, so inlined fonts and images pass; if you would rather not inline at all, set `build.assetsInlineLimit: 0`.

And one rule Vue itself sets: **precompile your templates.** Single-file components (`.vue` files) are compiled at build time, so they need nothing. A string `template:` option or an in-DOM template needs Vue's full build, whose runtime compiler calls `eval`, and HELMET's policy never allows `'unsafe-eval'`: the browser refuses it and nothing renders.

This recipe is proven in a real browser on every pipeline. `tools/vue-vite` is a small Vue app built exactly this way, and `tools/a11y/vue-check.mjs` serves its build in Chromium with HELMET's default headers and the swapped nonce. It checks that the app mounts with no CSP violation, its stylesheets and an inlined image load, a click updates the page, and a lazily imported chunk renders with its stylesheet carrying the response nonce. It also checks the two ways this goes wrong: the same build without the swap never mounts, and a runtime-compiled template is refused. To run it yourself, from the repository root:

```sh
php tools/a11y/corp-headers.php > build/helmet-headers.json
npm --prefix tools/a11y ci && npm --prefix tools/vue-vite ci && npm --prefix tools/vue-vite run build
node tools/a11y/vue-check.mjs --headers=build/helmet-headers.json
```

The latest recorded run is on the [Proof](https://helmet.apps.wayne.edu/docs/reference/proof.html#browser-checks) page.

## The environment ribbon [#](https://helmet.apps.wayne.edu/docs/guides/usage-raw-php.html#the-environment-ribbon)

`helmet_ribbon()` gives a raw PHP app the same ribbon the Laravel adapter injects, so nobody mistakes a test site for the real one. Print its `html()` right after your `<body>` tag, and style `.helmet-ribbon` (and `.helmet-ribbon-warning`) in your own CSS:

```php
use function Waynestate\Helmet\helmet_ribbon;

echo helmet_ribbon(getenv('APP_ENV') ?: 'production', true, getenv('HELMET_POLICY_PATH') ?: null)->html();
```

The old `Waynestate\Helmet\Ribbon\helmet_ribbon` name still works for one release and raises a deprecation.

It renders only for `local`, `development`, `dev`, `testing`, `test`, `staging`, `stage`, `qa`, `uat`, `preprod`, `pre-prod` and `sandbox`, in any case: the same list as Laravel (`Ribbon::ENVIRONMENTS`). Production, an empty name and any name it does not know get an empty string even when the second argument is `true`, so a typo in `APP_ENV` hides the ribbon rather than showing it on the live site. The third argument, a path to a CREED `policy.json`, adds a warning line when the running PHP version is in its security-only phase or end of life; a missing or broken file adds nothing and never breaks the page.
